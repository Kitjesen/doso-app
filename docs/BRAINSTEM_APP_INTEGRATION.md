# Brainstem 与 DOSO App 对接清单

架构总入口见[单一控制架构](design/DOSO_SINGLE_CONTROL_ARCHITECTURE.md)。新增接入前先确认应复用哪一个现有模块；不要新增第二套 SDK、控制会话或 gRPC 传输。

## 控制权与产品能力推进（2026-11-04）

目标是先完成一台机器狗的 App 手动控制闭环。以下为分工和验收计划，不代表已部署或真机通过；当前机器狗运行版本和 G20 安装包须在联调前重新核对。

| 层级 | 状态或来源 | 职责与边界 |
| --- | --- | --- |
| Brainstem 机器狗端 | 无人控制、gRPC 控制、机器人侧直连遥控来源 | 决定唯一控制者、租约、仲裁与失效停止；本地代码设计为机器人侧直连遥控优先，实际部署和抢占效果待核对 |
| App / G20 | 触屏摇杆、G20 实体摇杆 | 二选一接收输入，切换清除旧输入；二者经同一 App 会话发往 gRPC，不等同于机器人侧直连遥控来源 |
| 其他 App / 客户端 | 各自的 gRPC 会话 | 申请和释放由机器狗端决定；多个客户端的互斥、身份展示、抢占与释放须端到端验证 |

App 负责连接、输入、控制权申请/释放入口、反馈与状态过期显示；Brainstem 是控制权和执行结果的最终依据，负责授权、校验、仲裁、租约、动作执行、回执与本地失效处理。设备绑定或账号归属不等于实时控制权。连接成功不等于取得控制权；ACK 接纳不等于动作完成。界面优先使用简短中文，内部保留原因供诊断；停止未确认必须单独提示，不能归为普通失败。

## 期望机器人端配合

1. **稳定的只读状态**：无本地手柄时也初始化策略管理和状态数据源；明确反馈 FSM、控制者、租约、电机使能、故障、当前策略和可用策略。确保状态有可判断的新鲜度，离线或缺失值保持未知。
2. **电池与运动遥测**：提供真实电池电量或电池管理系统数据、机身实际前后/横移/旋转速度、通信质量和数据时间。`GetVoltage` 当前是各电机母线电压，不能直接当电池百分比；摇杆目标速度也不能当实测速度。新增字段时约定单位、坐标、时间基准和无数据语义。
3. **16 电机及多机型**：提供稳定的电机 ID、位置、速度、温度、力矩、在线状态和故障；核对真实机器的 ID 与 12 腿关节 + 4 足轮标签。不同机型应发布关节布局和能力清单，不能仅靠 App 的型号卡或 IP 判定兼容。
4. **真实控制和失效处理**：实现并测试租约、单调递增序号、ACK、输入超时、断线停止和本地手柄抢占；运动输出前再次核验电机许可、控制权、状态和故障。`WalkChecked` 使用机身坐标：x 前后、y 左右（m/s）、z 转向（rad/s）；符号、限幅和时序需双方以实际机器核对。App 当前输入新鲜度上限为 150 ms，原生运动 RPC 截止为 100 ms；服务端超时仍以服务配置与实测为准。
5. **姿态、电机和策略动作**：为站立、坐下、使能、失能、策略切换提供真实接受/失败及状态反馈。App 现允许站立或趴地、无活动租约时切换，不额外要求失能；机器人端必须实现相同门禁。策略 ID 和说明以机器狗返回的真实列表为准，不凭文件名推测模式，详见下节。
6. **停止与急停的清晰边界**：确认零速度、释放租约、失能和物理急停各自的行为。当前 proto 没有独立 `Estop` RPC，App 停止或页面退出不能冒充硬件急停；请提供真实停机及失联后的测试证据。
7. **连接与授权**：开发局域网模式仅用于明确隔离的联调。正式连接需要服务身份、客户端授权和证书校验；账户登录、设备绑定、机器人控制权是不同环节。不要将私钥或设备凭据提交到仓库，也不要以关闭证书验证解决连接问题。
8. **首次配网与后续实时传输**：BLE 首次配网需要机器人端提供身份校验、受保护凭据写入、失败恢复和 Wi-Fi 连接结果；后续状态和控制走 Wi-Fi/IP。未来目标是在 App 与机器人之间用 WebRTC 承载视频、音频、点云、状态和控制，机器人内部继续对接 Brainstem gRPC。信令、认证、传输配置、回执和失联策略尚需实现与验收，不能把目标架构当成现有能力。

## 连续速度的最新目标契约（2026-10-28）

目标：拥塞时只保留最新且仍有效的运动目标；保留现有WalkChecked序号、ACK、租约与失效停止。此节是双端契约，App实现与机器人实现分别验收，不能由一端通过推定全链路完成。

### 三类通路

| 类别 | 处理方式 |
| --- | --- |
| 连续速度x/y/yaw | 可覆盖的单个最新目标；只覆盖未发送/未消费的目标，不修改已发送RPC载荷 |
| StandUp、SitDown、SwitchProfile、Enable、Disable | 明确的离散操作与回执，保持已有忙碌/确认/顺序门禁，不放入速度覆盖槽 |
| 停止、失联、后台、抢占、故障 | 优先撤销旧意图、清空槽并使旧代际失效，再执行停止/清理；不能仅在普通FIFO末尾追加零速度 |

### App边界

最多一条速度RPC在途，另有一个完整待发快照。A在途时收到B、C，只保留C；A的ACK有效返回后，重新检查C的代际、来源、各轴时间、新鲜度、前台、租约、控制者与故障，仍有效才发送。A失败、超时或连接更换时直接丢弃C，不重连补发。状态读取占用期间同样只保留一个最新快照；受保护动作、停止和所有权变化清空它。

待发快照包含左右杆完整值、各轴JS接收时刻、会话标识/代际，以及G20原始Android单调采样请求时间。G20时间原样传给原生层，不能在出槽时刷新；触屏也保留原各轴接收时刻，不能把出槽时间当作新手势。两个时间域不能直接比较。回中/停止优先中断在途控制，不能被后续非零值覆盖掉。

源样本序号与网络序号不同。B未发送就被C覆盖时，不为B消耗网络序号；若A是WalkChecked序号41，C实际发送时仍是42。沿用原生层分配连续序号和逐条ACK检查，不允许为了跳过B而绕过服务端顺序保护。该机制改善拥塞时的新鲜度，但不产生50Hz采样或50Hz发送周期。

### Brainstem边界（待负责方实现与部署核验）

当前核查的本地代码是walkChecked准入后经ControlArbiter进入M.add；CMS使用asyncExpand串行处理，尚无容量1的待消费速度槽。Walking状态下覆盖direction只发生在事件已消费时，不能当作已经消除了队列。现有ACK代表命令通过准入并交给FSM，不代表已经应用到控制目标或电机。

1. 连续速度在实际消费边界保留一个最新目标，携带来源、租约/所有权代际、准入序号、机器人本地接收时间和固定失效期限。不能只在网络入口加槽，之后仍把每帧裸A.walk排入旧FIFO。
2. 接纳新速度可覆盖尚未消费的旧速度；消费前再次检查目标代际、租约、优先控制源、电机许可、状态、故障和期限。失效或被更高优先级来源抢占的目标不得更新Walk方向。槽取空后，已应用的active目标仍携带原固定期限，输出前持续复检，过期停止；不能只检查pending槽。
3. 停止/抢占/失联同步清空运动槽并使旧代际失效，不能等旧运动队列处理完才撤权；保留云卓优先级，不将整个CMS改为latest-only，否则会覆盖姿态、Fault或Done等离散事件。
4. 现有WalkChecked入口的准入序号仍逐条连续；已准入但被新目标替代的速度可以不应用。相同序号和载荷的重复请求复用原准入结果，不重置运动目标的接收时间或固定期限，不把过期目标重新入槽；租约续期与运动目标新鲜度分开。lastAcceptedSequence仅表示已接纳序号。若需反馈lastAppliedSequence，另行扩展状态契约，不能擅自改变既有字段含义。
5. Robot接收时钟与Android采样时钟不共享原点。现有WalkRequest只有token/sequence/direction，不能宣称机器人已经能独立核验150ms端到端源年龄。机器人本地消费期限与App源新鲜度分别保护；若需传递剩余有效期，须单独审查协议兼容、上限和网络延迟语义。

最低回归集：A阻塞后B被C覆盖；过期C丢弃且不续命；停止清空C；旧ACK/旧会话不能恢复C；云卓抢占后旧目标失效；站坐/策略动作不被覆盖；控制源切换必须重新回中；重复RPC不延长目标期限；pending为空但active过期仍停止；消费及输出前保护有效。50Hz另测源采样、发送、准入、应用频率和ACK/抖动，不用队列测试代替实机时序验收。

速度相关横移/yaw包络由机器人端按机型/策略统一约束，App可显示当前限制与请求值。智身GEN2中高速档的1m/s门槛和转向限幅只能作为参考，不能直接套用DOSO；本节不修改现有限速、增益或模型。

参考版本为 GEN2 `e8f959a22a6e5714bc299a551b45e1c182ac05c7` 的公开 SDK；这里不将 SDK 文档当作智身 App 的实机验证。采用功能语义，保留 DOSO 的硬件、协议与授权约束。

| P1 | 按机型发布能力、状态与速度限制 | 只显示真实支持的策略/动作，并给出不可用原因 | 统一发布能力和已验证的速度约束；普通加减速按实际 dt，失效停止不被平滑拖延 |

健康性判定：串行 FSM 适合管理姿态和离散事件，ACK 表示准入也合理；连续速度逐帧进入 FIFO 则无法保证拥塞后的意图新鲜度。当前本地核查只能证明这一结构风险，不能声称实际机器已经发生积压。完整验收仍需覆盖从准入、仲裁、消费到输出的时序和停止，App 单槽或 50Hz 发包均不能单独代替。

## 平地 / 楼梯槽位切换（2026-10-27）

App 已接通 Android 原生 gRPC 调用链，不经过网页服务，也不模拟云卓 R2 按键：

`运动模式按钮 → switchPolicy(实际 profile ID) → action("switch-profile", ID) → RobotControl.SwitchProfile`

| 接口 / 状态 | 调用与规则 |
| --- | --- |
| `GetProfile({})` | 返回 `current`、`available[]`、同索引的 `descriptions[]`、`current_description`；ID 是实际配置名，不是固定模型文件名 |
| 槽位映射 | 槽位版机器人在说明中使用 `flat: ...` / `stairs: ...` 前缀；App 据此前缀绑定目录中的实际 ID，也兼容目录直接使用 `flat` / `stairs`。不按列表顺序、W5/CTS 文件名或中文描述猜测；重复绑定不开放模式按钮 |
| `SwitchProfile({"name":"<available 中所选实际 ID>"})` | 请求字段 `name=1`；返回 `ProfileInfo`。原生层核对返回 `current` 等于目标 ID，界面仅以设备回执/后续状态确认，不乐观假定成功 |
| Standing / Grounded | 允许切换；使能或失能均可。需无活动 gRPC 租约、无关键电机故障、无云卓占用，状态新鲜且无操作在途 |
| Walking / Zero / Transitioning | 禁止；即使 Walk 速度为零也不能切换。不自动排队或重试 |
| 高台为空 | 显示不可用，不发送请求，不拿平地模型冒充高台 |

操作员：先释放 App 运动控制，确认设备实际处于 Standing 或 Grounded，再点平地/楼梯并确认。切换仅更换机器人预加载策略，不自动使能、起立、趴下或行走，不修改增益、限位或限速。不同策略的观测历史由机器人端各自管理，App 不拼装 ONNX 输入。

**Walking → Standing 需要配套机器人补丁**：App 在电机已使能、无活动 gRPC 租约、无云卓占用、无关键故障、状态新鲜且无操作在途时，允许从 Walking 显式调用 `StandUp`。机器人必须部署支持 Walking 下在零命令、无活动租约后派发既有 `A.standUp`、并拒绝忙碌/切换状态的版本；未修补版本不保证回到 Standing。流程为停止并释放租约 → 手动点站立 → 等设备实际回报 Standing → 再切换平地/楼梯。松杆、释放、刷新状态均不会自动起立或切换；Walking 和姿态切换期间仍不可切换策略。旧机器人应继续使用停止并释放 → `SitDown` → 等 Grounded → 切换 → `StandUp` 的流程。

## 推荐联调顺序

1. 先在离线 fixture / 仿真中核对 proto 编解码、状态字段、拒绝原因和动作 ACK。
2. 在真实机器人上先做只读状态与设备身份检查；逐项记录源码版本、协议哈希、App 安装包哈希、测量时间和结果。
3. 单独验证控制权、失联和停止链路；现场条件明确后，才逐项验证使能、姿态和低速动作。
4. 再推进 BLE 配网、视频/点云传输及跨型号能力。不能用网页预览、TCP 可达或单次模拟成功代替真实设备验收。
