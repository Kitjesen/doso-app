## 2026-11-04：UUID 绑定与三项设备信息

按最新产品决定，对外设备信息统一为机器人 ID、机器人版本、固件版本。永久 ID 使用云端 `devices.id` 的 UUID v4，设备保存到现有 `agent.env` 的 `DOSO_DEVICE_ID`；LingTu SDK 与云端 Agent 共享读取，升级和解绑不重新生成。

UUID 由系统处理，客户无需输入编号或绑定码。首次连接的产品流程确定为“发现附近机器人 → 扫描随设备提供的专属二维码 → 在 App 确认绑定”。机器人本体没有配对按键或确认屏幕。

专属绑定二维码格式为 `doso://robot/<UUID v4>?claim=<一次性凭据>`，包含云端已登记的永久 ID 和受保护的认领凭据。App 扫码后显示识别结果，点击“确认绑定”才提交，凭据仅保留在本次内存中。公开的 `doso://robot/<UUID v4>` 只承担设备标识，扫码页提示用户改扫随设备提供的专属绑定码。相机拒权、取消和错误提供返回与重试。

现有管理端临时绑定码默认10位、有效30分钟，后台可配置最长一天。随设备二维码使用管理端 action `issue_factory_claim`，生成32位随机凭据，仅返回一次含凭据的二维码内容，云端复用摘要存储、尝试限制及一次性消费事务。到期时间由工厂或运营按交付批次明确提供，重新签发会使旧印刷码失效。该接口已有13项Deno及23组隔离PostgreSQL验证记录，包含工厂签发与竞争检查。正式工厂制码、发放和真实扫码仍待验收；2026-11-07模拟流程使用正常API绑定，不作为工厂专属二维码上线证明。[数据库验证证据](../../artifacts/multi-device/2026-11-03T19-37-15-600Z/verification.json)

App源码已支持BLE候选连接后读取GATT设备UUID，并将读取值与专属二维码UUID核对。系统外设ID只用于发现，UUID一致不代表设备签名验证完成；首次开机自动广播、绑定前挑战、制造签名及配网仍待接通和真机验收。具体实现边界见 [BLE配网](ROBOT_BLE_PROVISIONING.md)。

App 请求、超时补查和取消后的确认统一使用扫码取得的 UUID；设备资料、列表及身份验证页显示机器人 ID。机器人版本显示已有 `devices.model_code`，固件版本原样显示 `devices.firmware_version`，缺失保留待同步。

云端新请求使用 `{action: "claim", deviceId, code}`。新 UUID RPC 维护唯一认领事务；已安装旧 App 的 `serialNumber` 请求和旧 RPC 只解析到同一设备 ID 后转发。一次性绑定码、所有者检查、并发锁与解绑语义保留，库存序列号不再作为新 App 的认领输入。

UUID 认领底层已通过完整 TypeScript 检查、绑定与资料页行为、App 请求及超时/取消回归、21 项 Deno 检查、18 组真实 PostgreSQL 升级/权限/并发检查。数据库证据见 [UUID 认领验证](../../artifacts/multi-device/2026-11-03T16-54-54-786Z/verification.json)。

先前公开 ID 扫码版已通过 15 项扫码/请求行为检查、完整 TypeScript 检查与布局合同检查，这些记录不覆盖本次专属二维码改动。Expo 原生配置解析确认 Android 相机许可启用、iOS 用途说明为扫码、未申请麦克风。专属码解析与显式确认界面已在源码实现，专属码与导航的 18 项本地行为测试通过。新增相机模块仍需重新构建原生安装包，手机实拍扫码和真实设备认领尚待验收。

后续交付包括新版迁移、Functions 和包含相机模块的 App，Agent 对 SDK 三项信息的可信上报，以及真实设备 UUID 核对、专属凭据签发和受保护二维码制作。App 产品目录与 `vendor/model` 的正式对应关系仍待确认，资料页保留设备记录中的型号。实机扫码、BLE 身份匹配、设备证明与固件安装各自验收。

## 产品主线：按四个阶段交付

根据森哥提供并认可的《机器狗绑定方案梳理》修订。设备身份回答“它是谁”，配网回答“怎么通信”，账号归属回答“属于谁”；终端凭据与控制租约是落实授权的技术层，不应成为普通用户的证书安装流程。

| 阶段 | 谁来做 | 完成条件 |
| --- | --- | --- |
| 工厂建档 | 工厂工具、设备后台 | 唯一Device ID与SN、制造身份、硬件/软件版本和批次对应正确；owner为空，不预先认领到工厂个人账号 |
| 工厂检测与放行 | 测试工位、设备后台 | 启动、通信、身份与该型号规定的安全/硬件检查有真实记录；合格后标记待激活；未通过不得出货 |
| 用户首次认领 | 用户、App、机器狗、后台 | 登录→附近发现→扫描专属二维码→App确认→验证凭据及真实设备→后台原子确认归属→按需配网 |
| 日常与售后 | 所有者、获准成员、受控售后 | 换手机恢复设备列表；共享不改所有者；转售、退货、换主板有明确移交和再检测记录 |

工厂测试权限应是独立的受控授权，交付前撤销或关闭，不作为永久售后后门。成套G20可以预装App并预配通信，但不因此获得客户账号归属；普通控制仍受正式授权约束。本文列出的工厂硬件检测是未来放行要求，不是本轮真机动作授权或通过记录。

状态分别记录，不能混成一个`is_bound`：出厂配置/检测结果、账号归属、运行健康与在线状态互不代替。关机/断网不清归属；已配置身份不等于检测通过；检测通过不等于已有用户认领。

基于既有需求，首版采用：BLE用于附近发现/首次配网（硬件可用后启用），Wi-Fi/有线承载本地控制；云端负责账号、归属及管理。已经授权的本地控制不以每次公网登录成功为前提；首次认领/移交通过在线后台确认，完全离线首次认领属于另行定义的部署模式。一个所有者可管理多台机器狗并邀请成员。公网实时遥控不是本轮新增范围。

量产产品主线为：设备档案/出厂记录→认领事务与真机证明→多机选择→共享和售后→真实配网及OTA。按森哥最新优先级，当前先完成一台G20与现有机器狗的真实连接，再按现场授权验证控制；量产后台、BLE与OTA不挡住这一工程联调。具体当前进度统一见[SINGLE_ROBOT_APP_ACCEPTANCE.md](SINGLE_ROBOT_APP_ACCEPTANCE.md)，工程配对不替代用户认领闭环。

## 1. 下载App后的使用关系

下载DOSO不会自动获得附近机器狗的控制权。用户登录后可认领自己的机器狗，或接受所有者的共享授权。产品目标：一个账号可拥有多台机器狗；每台机器狗有一个明确所有者，允许多个设备成员；同账号可使用多台终端；一个终端可以保存多台机器狗。多端可观察，运动控制保持单一租约及物理控制优先级。

首版设备成员角色建议收敛为：owner管理与移交；operator在设备条件满足时申请控制；viewer只查看获准数据。平台support/admin不是设备成员角色。共享邀请须限定设备、接收账号、权限、期限和使用次数，撤销须同时影响新的访问与已有授权续期。离线授权的剩余有效期应明确，不能承诺无法联网的终端即时收到云端撤销。

当前实现的真实限制：

- `public.devices`已有`id/owner_id/serial_number/model_code/firmware_version`；一台设备的序列号唯一。
- 2026-11-03新增的多设备迁移移除第二台限制，设备唯一身份、认领码与事务权限继续保留；相关迁移已有2026-11-04部署记录。真实多台实体设备的使用验收仍待完成，详情见[多设备进度](DOSO_MULTI_DEVICE_PROGRESS_20261103.md)。
- App已有设备列表、添加、选择、切换以及解绑后保留其他设备，按账号保存当前设备选择；没有保存选择时使用列表候选。当前活动设备保持单个，真实多台实体设备的切换与控制仍待验收。
- 当前没有设备成员、共享邀请与设备角色授权表/流程。不能用同账号多终端冒充多账号共享。

多机改动覆盖迁移、claim事务、Edge错误契约、数据库测试、App设备选择及切换时旧输入/身份/租约清理。相关部署和本地结果分别见[多设备进度](DOSO_MULTI_DEVICE_PROGRESS_20261103.md)；真实多台实体设备验收仍待完成。本次文档核对没有执行新的生产迁移或权限变更。

## 3. 一次明确的配对授权如何完成

归属绑定与终端配对各有一个结束条件。修订后的产品首次认领流程为：

1. 用户登录后查找附近机器人，扫描随设备提供的专属二维码，App 取得永久 UUID 和一次性认领凭据。已属他人的设备只给出通用提示，保护原用户信息。
2. 用户在 App 点击“确认绑定”，后台验证凭据并开启限时认领申请，此时处于待确认状态。
3. App通过BLE或局域网与目标设备完成制造身份挑战应答，证明来自指定设备；把证明绑定到该次申请、账号、终端和有效期。BLE广播、单纯连通和CSR持钥证明都不替代认领授权。
4. App 提交完整证明，后台在同一事务中复核 UUID 匹配、设备仍可认领、凭据未消费和证明未过期，然后写入 owner 并消费凭据。并发只能一人成功，失败或断网保留明确待确认状态。机器人尚未联网时显示“已绑定，设备待联网”，随后按需配网。
5. 系统自动建立当前终端正常使用凭据，并取得真实状态。客户端私钥保留本机；证书/CSR属于内部实现，普通用户不处理P12文件或找工厂给新手机手工签发。
6. 申请控制租约与使能仍是后续显式动作；配对完成或连接恢复不自动运动。

**当前代码不能直接按此顺序运行。**`claim_device_with_digest`现在先写owner并消费码，`device-enrollment.begin`又要求设备已由当前账号拥有。因此必须新增或改造受控的“待认领申请→真机证明→原子完成认领”服务端流程，保留限次/过期/会话和恢复出厂计数检查；不能仅把UI按钮调换顺序或删除begin的owner校验来冒充完成。现有已归属用户的终端入网可以继续复用begin/attest/complete，但新机认领要有明确的独立入口和事务边界。此处仅修订设计，未改数据库或后端权限。

换手机/G20时登录原账号恢复设备列表，不重新消费机器狗认领码、不改变owner。新终端仍需通过账号/设备授权验证并建立自己的凭据，旧终端可单独撤销；不承诺仅知道账号名就自动取得控制。添加第二只机器狗须为该设备单独验证授权，不能复用第一只狗的许可。成套预配、账号归属及最终控制权仍独立管理。

2026-10-25 的工程接入先用可信 USB 与受控工厂签发完成 CSR。最新用户首次认领采用专属二维码和 App 确认，已有所有者的终端授权继续遵守归属检查。设备本体没有确认按钮或屏幕，配对流程保持现有电源、复位和急停的职责。

### 售后和异常场景

| 场景 | 产品处理规则 |
| --- | --- |
| 机器狗离线或关机 | 保留owner和成员；更新在线状态，不执行自动解绑 |
| 恢复出厂 | 可清网络/用户偏好并失效本地运行授权；保留制造身份和云端归属，不默认清标定；原主人重新验证后恢复 |
| 原主人转售/转移 | 明确批准受让方或走受控售后核验；更新归属并失效旧成员/终端许可，保留设备档案和历史记录 |
| 解绑 | 撤销相应归属/授权关系，不删除整机档案；可否重新认领须满足定义的交付状态，不能无条件抢领 |
| 返修/更换主板 | 保存整机SN、旧/新硬件身份和维修关系；撤销旧板有效身份，重新检测，防止旧新板同时冒用同一设备 |
| 退货再销售 | 审核交接、清理客户运行授权与数据、检测、重新放行；不可只删owner字段就当新机 |

这些流程包含新的数据库/授权逻辑与撤销验收，当前仍待实现。不得依据本文自行删除账号数据、重置设备或执行权限迁移。

## 4. 蓝牙适合承担什么

参考宇树Go2，推荐BLE用于附近发现、首次身份挑战和少量配网数据；Wi-Fi/有线IP用于Brainstem gRPC与视频。把家庭/现场Wi-Fi凭据发给机器人必须走已经鉴别身份且加密的通道，凭据不写聊天、日志、公开记录。BLE连接与Wi-Fi连接各有明确失败状态；断网不能显示假配网成功。

现有App已有Android/iOS扫描、连接、服务发现及断开，并能读取只读GATT设备UUID。设备签名挑战、配网写入及通知尚未实现；`provisioningGateway`中的模拟状态机不代表真实配网。手机扫描、读取、专属二维码与机器人广播仍待真机联调，详见 [BLE配网](ROBOT_BLE_PROVISIONING.md)。

历史真机只读结果（2026-10-25 22:12—22:24，Asia/Shanghai），今天的控制器状态仍需重新采集：

- 主机为RDK S100 V1P0；BlueZ 5.64服务运行，内核有hci_uart/btbcm。
- `/sys/class/bluetooth`没有控制器；`bluetoothctl show`报告No default controller available；`btmgmt info`为0项。
- `hobot-bluetooth.service`反复在XM612固件下载超时，保留日志显示重试计数293；没有本轮启动/重启它。
- PCIe Wi-Fi枚举为RTL8822CE，USB清单没有蓝牙适配器。这不证明板上物理绝无蓝牙，但足以判定当前系统无可用BLE控制器；XM612初始化与实际模块匹配仍需核实。
- 官方S100接口文档说明M.2 Key E为PCIe Wi-Fi加四线UART蓝牙，不提供USB/SDIO；适配必须核对具体模块，不能只看“支持蓝牙”字样。

本阶段不依赖蓝牙才能推进受控局域网接入。后续先修/验证板端hci控制器与LE能力，再实现认证GATT，最后启用App真实配网入口。未擅自刷固件、购买模块或改无线配置。

官方资料：https://developer.d-robotics.cc/rdk_doc/en/rdk_s/Quick_start/hardware_introduction/rdk_s100/ ；https://developer.d-robotics.cc/rdk_s_doc/System_configuration/network_bluetooth

## 5. OTA现状与最小产品范围

现有领域状态机和离线模拟器覆盖下载哈希、签名、健康确认及回滚流程；正式App配网/OTA路由仍为不可用页面。`firmwareUpdateGateway`含模拟manifest与人工健康证明；通用设备命令目前只有diagnostics.health_check。没有生产OTA作业/API、机器人下载安装器或真实启动回调。

先将三种更新明确分开：DOSO APK升级、Brainstem应用版本更新、系统/BSP固件更新。首个机器人OTA里程碑建议只做Brainstem应用版本更新，不把系统内核和标定一起打包，也不把开发PC的SSH部署工具称为OTA。

首版真实闭环必须包括：签名发布清单及机型/硬件兼容信息；设备报告当前版本；明确授权的更新作业；下载/哈希/签名校验；安装前机器处于允许维护的状态；候选版本隔离；切换后健康与版本证明；失败保留旧版及可复现回退；进度和错误回传。断电恢复、空间不足、签名错误及旧版本降级策略都需测试。具体端点/工作进程待实现，不展示“更新成功”的模拟结果。
