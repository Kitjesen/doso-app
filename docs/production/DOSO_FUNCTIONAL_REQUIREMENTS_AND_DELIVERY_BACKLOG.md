## 产品中的三个层次

1. **地图**回答机器狗在哪、环境是什么，是数据和定位的展示。
2. **路线**回答按哪条路径移动，引用确定的地图版本与经过验证的点/边。
3. **任务**回答到哪些位置做什么，组合路线与已支持动作。召回是指定目标的导航操作，需要独立检查与反馈。

地图浏览不要求运动控制权；运行路线、任务和召回需要机器人确认权限、位置与执行条件。界面不得从“地图加载成功”推导“可以移动”。所有执行页区分提交中、已接受、执行中、完成、失败、取消和状态未知；ACK 只表示请求已接纳，完成以设备结果为准。

## 地图首版需求

| ID | 首版要求 | 验收 |
| --- | --- | --- |
| MAP-01 | 显示机器人导航系统实际提供的 2D 地图；保留缩放、平移、回到机器人位置 | 使用真实地图源；不把效果图当实际地图。断开后最后地图可保留，实时位置明确失效 |
| MAP-02 | 地图标识、版本、坐标系、分辨率/单位、原点与校验值完整；App 将机器人坐标正确转换到显示坐标 | 已知点、角度与距离对照正确；地图翻转、单位/坐标系不匹配、错误校验值均不能执行导航 |
| MAP-03 | 显示机器人位置、朝向、定位有效性和数据新鲜度 | 失去定位、定位质量不足、过期、重连与地图更换都不会继续显示假实时位置 |
| MAP-04 | 点位包含稳定 ID、名称、位置和朝向；可查看地图上的点位和指定返回点 | 地图版本改变时旧点位须重新核对，禁止默默沿用旧坐标 |
| MAP-05 | 控制页在有真实地图时可切换地图/视频；操作按钮、停止入口和控制状态保持可见 | 手机和 G20 横屏可用；切换视图不会改变控制来源、发出动作或恢复旧输入 |

依赖：机器人导航组件实际存在并能提供地图和位姿；当前 Brainstem 控制 proto 的存在不能证明定位/建图已提供。先核对机器狗导航栈，再冻结传输协议，避免 App 单方面定义出机器人无法提供的数据。

首版不要求手机端建图、在线多人共同编辑、自动语义识别或多层楼地图。

## 路线首版需求

| ID | 首版要求 | 验收 |
| --- | --- | --- |
| ROUTE-01 | 路线属于机器人/地图版本，包含 ID、修订号、名称、按序点位及几何校验值 | App 列表来自真实存储；模板仅用于说明，永远不能直接运行 |
| ROUTE-02 | 首版编辑方式为选择已有点位并排序；保存前验证点存在、边连通、长度与地图匹配 | 重复/缺失点、断开边、未知地图、NaN/越界坐标均被拒绝 |
| ROUTE-03 | 运行前展示路线与目标，机器人重新核对定位、地图版本、权限、故障和是否已有执行任务 | 未满足条件有明确原因；双击和重发不会产生第二个执行实例 |
| ROUTE-04 | 展示运行实例 ID、当前路段/点位、执行阶段、失败原因；提供暂停、继续、取消 | 继续需要重新检查当前条件；停止/取消的接受与停止确认分别呈现 |
| ROUTE-05 | 重连按运行实例查询真实状态，不重发启动 | App 重启、切后台、网络断续不产生重复路线；未知结果不显示成功 |

路线执行由机器人导航执行器完成；App 不通过不断发摇杆速度来模拟自主路线。遇障的停止、绕行或失败策略需要导航团队明确；首版不承诺自动绕障，真实能力未经证明时应停止并报告。

| TASK-02 | 任务定义和运行实例分开；定义有机器人、地图/路线版本、修订号与步骤；实例记录实际结果 | 编辑定义不改变运行中的旧实例；步骤结果绑定实际实例/步骤 ID |
| TASK-03 | 显示总任务与当前步骤的状态；明确失败时停止还是跳过，首版默认失败停止 | 提交失败、执行拒绝、步骤失败、超时和取消都可区分；未执行步骤不能标成功 |
| TASK-04 | 冲突仲裁：同一机器人最多一个自主运行实例，人工控制接管必须经过设备端停止/交接确认 | 两个客户端同时启动、人工介入、重连均不会并发运动 |
| TASK-05 | 保存开始/结束时间、步骤结果和固定错误码，敏感媒体独立授权访问 | 用户能解释本次是否执行、停在哪一步；日志无令牌、密码或完整视频内容 |

日历日期选择暂不代表已具备定时任务。定时/周期任务、自动回充、跨网络远程启动和无人值守运行放在一次性任务闭环之后，分别增加时区、到期、断网与权限验收。

## 召回首版需求

首版建议将“召回”定义为**返回当前地图上预先确认的返回点**。返回用户手机位置、返回起点、返回充电座是不同目标，不共用模糊的“召回成功”。若产品要改成跟随用户，需另加可信用户定位和跟随策略。

| ID | 首版要求 | 验收 |
| --- | --- | --- |
| RECALL-01 | 运行前显示返回点名称及地图位置；没有返回点不能启动 | 目标和地图版本经过设备核验，坐标从真实保存点取得 |
| RECALL-02 | 与路线共用导航执行与运行实例，不另造一条无状态速度通道 | 任务运行时明确停止/交接；不能同时启动任务和召回 |
| RECALL-03 | 展示规划、返回中、到达、受阻、取消或未知；提供停止 | 到达由导航定位和容差确认；不能用请求成功、计时或最后一点已发出当到达 |
| RECALL-04 | 定位失效、地图变更、控制权丢失或链路异常按机器人本地策略处理 | 断网后仍受本地保护，App 恢复后读取真实状态；停止原因有记录 |

回充只有在充电座定位、精确对接和电气充电确认都提供后才开放。回到充电座附近不能显示“回充完成”。

## 扩展动作怎么接

先接“查询设备支持的动作目录”，再开放执行。当前平地/楼梯/高台属于策略模型切换，沿已有 `GetProfile` / `SwitchProfile` 路径；拜年等完整动作沿独立动作系统，不能把策略文件名当作动作。

| ID | 首版要求 | App / 机器人职责 |
| --- | --- | --- |
| ACT-01 | 真实动作目录有稳定 ID、名称、版本、适用机型、允许的姿态/电机状态、可取消性 | 机器人只发布已配置并经过验证的动作；App 未收到目录时显示无可用动作 |
| ACT-02 | 每次执行绑定动作 ID/版本和请求 ID，设备做最新条件检查 | App 只发意图；机器人校验状态、模型、控制归属及运行冲突，不信任界面的 enabled |
| ACT-03 | 动作状态可观察，区分接纳、过渡、执行、结束、取消和失败 | `PlayGesture` 当前 Empty 返回值本身不足以证明完成；需在现有 FSM/状态流补齐可关联的执行身份与结果，或正式扩展协议 |
| ACT-04 | 停止策略按动作定义确认，物理急停仍是独立能力 | 不能把通用“停止行驶”改名后当硬件急停；中途取消不允许跳过必要安全过渡 |
| ACT-05 | 一次只验证一个动作包 | 用模拟模型核验状态机，再在固定/安全场地验证各动作条件；未验收的“拜年”不可因目录存在就开放 |

首版不开放用户上传任意脚本、任意动作文件路径或无检查的批量播放。服务端 `ListGestures` / `PlayGesture` 需先实现，不能只加 App 按钮。

## OTA 怎么做

首版真实 OTA 的实施合同已经整理到 [DOSO OTA 实施计划](DOSO_OTA_IMPLEMENTATION_PLAN.md)。先按该合同完成 Brainstem 应用与兼容策略包的单机更新代理，再开放 App 生产入口。

App 自身 APK 更新、Brainstem 应用更新、策略模型更新、主机系统/内核更新和电机固件更新是不同的发布对象。首个真实 OTA 建议仅覆盖 **Brainstem 应用与兼容策略包**；驱动/内核/电机固件后置。现有离线 OTA 模拟可复用状态机与界面，不能直接复用模拟的成功事实。

| ID | 首版要求 | 验收 |
| --- | --- | --- |
| OTA-01 | 制品清单包括版本、目标机型/硬件、依赖版本、大小、哈希、签名、兼容规则和发布通道 | 签名由可信发布方验证；错误机型、损坏包、失效签名和禁止降级均被拒绝 |
| OTA-02 | 独立更新代理下载到暂存区、校验和预检；控制服务不接收任意 shell 命令 | 空间不足、断网、重复提交、下载中断均有可恢复状态；不会部分覆盖正在运行的版本 |
| OTA-03 | 安装前检查设备供电、空闲、无运动/任务、运行权限和可恢复版本 | 当前没有电池 SOC 时不能伪造“电量达到阈值”；须提供经验证的供电条件再开放安装 |
| OTA-04 | 应用/模型以不可变版本目录安装并原子切换；只重启更新对象 | 标定、网络、设备身份、账号归属及用户数据有明确保留策略，重启后核对实际版本 |
| OTA-05 | 更新完成须通过启动与协议/传感器/模型健康确认，再确认提交 | 安装命令返回、进程出现或端口打开不能单独作为健康通过 |
| OTA-06 | 健康失败或中断回退上一已知可启动版本，重连可查询实际结果 | 进程崩溃、模型不兼容、切换期间断电分别测试；不能只在界面演示“已回滚” |
| OTA-07 | 发布分为内部单机、少量试点、扩大范围；支持暂停后续推送 | 每批有版本/设备/结果记录；失败包撤回不自动卸载正在运行的稳定版本 |

第一版无需复杂自研 OTA 平台；先证明一个受保护更新代理可以对单机完成签名校验、保留数据、版本切换与实际回退，再接 App 作业管理和量产发布。密钥由发布侧受控保管，App 和机器人中只放需要的验证公钥；不能把签名私钥打进 APK。
